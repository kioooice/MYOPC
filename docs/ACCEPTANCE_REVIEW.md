## 需要收口的问题

### R1 / P1：过期客户端能把旧内容提交成“最新版本”（已复现）

位置：lib/business.ts 的 createVersion（约 235–254 行）、updateProject（约 133–156 行）；scripts/continuity-client.ts revise。
场景：A/B 都读 v1；A 提交 v2，B 仍基于 v1 提交不同内容。服务返回 201，把 B 的内容追加为 v3，并自动将 previous_version_id 指向 v2；即使载荷声明 previous_version_id=v1 也被忽略。旧版本仍在，但真实修订基线被错误记录，最新内容可能丢失 A 的改动。
项目更新也没有 revision 校验；连续携带相同 expected_revision 的两次修改都返回 200，后写覆盖前写。现有测试仅证明尝试 updateTrial 的冲突保护，不能将 TASKS 中“版本冲突保护”概括为全局成立。
结果要求：过期写入能明确冲突或显式分支，不伪造父版本；项目可变信息有相应冲突语义。具体实现由执行模型决定。

### R2 / P1：项目“最新成果”取错，甚至显示没有成果（已复现）

位置：lib/business.ts hydrateTrial、projectSummary、getProject（约 300、322–362 行）。
项目按行动 updated_at 取第一项，该行动的成果按 created_at 升序取第一项。提交新成果/版本未同步推进行动时间。
复现一：同一行动先创建“旧成果”、再创建“新成果”，latest_deliverable 返回旧成果。
复现二：项目已有两份成果，再创建一个尚无成果的新行动，项目列表和详情的 latest_deliverable 同时返回 null。
结果要求：当前行动和最新成果独立而准确地选择；新版本推进后能被找到，导航指向该成果真正所属的行动。若允许显式当前行动，也应明确语义，不能靠数组第一项猜测。

### R3 / P1：待审阅仍没有成为成果状态（静态审查）

位置：app/page.tsx 78、128、213、221–228、233 行，以及 acceptVersion。
待处理完全由开放反馈计算。新成果尚无人反馈时，待处理为 0；增加 feedback.kind=review 只是给意见加标签，仍需要额外制造一条审阅反馈。旧版已采用后再提交新版，成果列表与标题继续显示“已采用”，因为只检查 accepted_version_id 是否非空；最新版本是否待审阅没有进入待办。accept 也不处理 review 意见的状态。
结果要求：待审阅由具体成果版本及其审阅状态决定，与待修改反馈分开；保留旧版采用事实，同时明确新版等待判断。用户不应先写一条“请审阅”才能看到待办，不以自动采用或测试反馈补齐流程。

### R4 / P2：新的决策不能更新接续下一步（已复现）

位置：lib/business.ts 335、361 行；app/page.tsx 233 行。
start 时 next_step=“旧下一步”，随后通过通用客户端对应的 createDecision 写“新下一步”，getProject 仍返回“旧下一步”。因为 trial.next_step 永远优先于最新决策；页面顶部和下方最新判断可能互相矛盾。
结果要求：为当前下一步建立一致规则；执行模型通过受支持的工作流更新判断后，项目页、上下文和行动页一致，不要求反复维护同一信息的两个副本。

### R5 / P2：默认重试链路仍可能产生重复写入（静态审查）

位置：scripts/continuity-client.ts 25–26、请求与各写入输出；app/page.tsx 93、104、118 行。
客户端默认随机 ID 只在成功后打印；如果服务已写入但响应丢失，用户拿不到自动生成的 ID，重跑会生成新 ID。网页重试也每次生成新 ID。显式 --request-id 的重放是有效的，但不能据此概括默认失败恢复已完整。
结果要求：同一次不确定写入的重试能够保留原请求身份/载荷；明确代码推送与业务写入各自结果，不因一个成功而宣称全部共享。
